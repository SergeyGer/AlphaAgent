# Reproducing the public demonstrations

This page gives the exact command, requirements, output and review checklist for
every offline demonstration the project publishes. None of the five commands
below calls a language model, needs an API key, or makes a network request. The
one-time setup (installing dependencies, pulling container images) may use the
network; the demonstrations themselves do not.

## Which demonstration is which

The mode label matters, and one label used to be wrong. The Streamlit page is a
**risk-guard demonstration**, not the live React application. It is shaped like
the dashboard, but it runs one pure function on unsaved objects.

| Demonstration | Accurate mode label | What it is not |
| --- | --- | --- |
| Offline Streamlit demo (`demo/app.py`) | **Offline risk-guard demonstration** using the real `services/execution.evaluate_proposal`; no database, no LLM, no network | Not the live React dashboard; not the agent debate; attribution and theses are described, not executed |
| Decision-detail replay | **Recorded synthetic fixture replay** from `docs/spec/fixtures/decision-runs.v1.json` in a local database | Not a live model run; not a new decision; not market evidence |
| Offline decision viewer (`docs/viewer/index.html`) | **Static replay of a checksummed synthetic fixture bundle**; no Django, PostgreSQL, Redis, login or model key | Not live analysis; not execution or approval; not a new decision |
| Paper allocation | **Synthetic paper allocation** with a stubbed CIO (`provider: stub`, `source: fixture`) | Not live allocation; not realised performance; not an optimizer |
| Report build | **Synthetic Phase 3 measurement harness** (`engineering_validation_only: true`) | Not a protocol comparison; not a profitability result; no model call |
| Live stack (`docker compose -f docker-compose.ghcr.yml up`) | The real Django + React application | Not covered by the five commands here; it needs a browser session, and without an LLM key it runs the deterministic fallback |

The walkthrough video is a recording of the live application. It is not
regenerated by these commands, and it is not a substitute for the evidence in
[`CASES.md`](CASES.md).

## One-time setup

The five demonstrations need Python 3.12 and the repository's virtual
environment, except the offline viewer, which needs Node and the frontend
dependencies. The three database-backed ones also need PostgreSQL and Redis, and
a `.env` that passes the project's startup checks.

```bash
cd /root/projects/AlphaAgent

# Dependencies (already installed in the project venv; this is the full set)
venv/bin/pip install -r requirements.txt

# Local configuration. POSTGRES_PASSWORD and DJANGO_SECRET_KEY are mandatory.
cp .env.example .env
# edit .env: set POSTGRES_PASSWORD and DJANGO_SECRET_KEY

# Data tier
docker compose up -d db redis
venv/bin/python manage.py migrate
```

No `AI_LLM_API_KEY` is needed. Leaving it empty selects the deterministic engine;
the five commands below never ask for a model. `config/settings.py` still
requires `POSTGRES_PASSWORD`, so a completely empty `.env` will fail at import.

## 0. Verify the application before recording anything

A recording is only evidence if it names a verified commit. The one command that
runs the backend tests, frontend tests, type check, build, lint, migration check
and a running-stack smoke test is:

```bash
venv/bin/python scripts/verify_application.py --record
```

It prints one line per stage plus `VERIFY_SUMMARY {json}` and exits non-zero if
any stage fails. On a clean tree it writes
`docs/spec/acceptance/<commit>.json`; `record_live_allocation` refuses to run
from a dirty tree or without that record, and
`venv/bin/python manage.py check_recordings` confirms every committed recording
names the record's commit and digest. The schema, refusal codes and the
commit/record ordering are in [`ACCEPTANCE.md`](ACCEPTANCE.md); this page only
quotes the commands. At HEAD `7969cd7` the committed record is the four-stage
steps 9–10 record, not a full eight-stage pass; the gap and its evidence table
are in [`ACCEPTANCE.md`](ACCEPTANCE.md) §5 and tracked as
[#65](https://github.com/SergeyGer/AlphaAgent/issues/65).

## 1. Offline Streamlit demo

**Command** (from the repository root, because the demo imports `services/` and
`core/` from there):

```bash
venv/bin/pip install -r demo/requirements.txt
venv/bin/streamlit run demo/app.py
```

If `venv/bin/streamlit` is not present, `python -m streamlit run demo/app.py`
with the same environment works.

**What it needs.** Streamlit and Django only (`demo/requirements.txt`). No
database, no `.env`, no Redis, no API key, no network call from the demo code.
The app configures a minimal Django settings module at import time with
`DATABASES = {}`; it builds unsaved `Portfolio` / `PositionState` objects and
passes them to `services/execution.evaluate_proposal`.

**What it produces.** A local Streamlit page (by default
`http://localhost:8501`) with a dark dashboard shell, seven metric cards, two
portfolio-ceiling meters and tabs for the guard playground, the debate
description, decision quality, position thesis and About.

**What to look for.**

- The **guard playground** sliders are live: cash, `max_trade_allocation_pct`,
  `daily_loss_limit_usd`, `max_portfolio_exposure_pct`,
  `max_ticker_concentration_pct`, realised P&L, other holdings, price, side and
  size.
- The nine presets exercise a normal trade, a per-trade clamp, a zero budget, a
  breached daily loss limit (BUY blocked, SELL still allowed), an oversized SELL
  clamped to the position, a portfolio-exposure clamp, a concentration clamp,
  both ceilings binding (the smaller headroom wins), and a buy refused because a
  ceiling leaves no headroom.
- The verdict shows `ALLOWED` / `REJECTED`, the guard's **verbatim** reason
  string, any clamp note naming the binding ceiling, and the raw `GuardDecision`
  JSON.
- The Decision quality and Position thesis tabs say **"Not executed on this
  page"**. That is the accurate label: those paths need a database and, for
  attribution, price history. The page describes the real implementations; it
  does not simulate them.
- The About tab's "Which guard rules this page exercises" expander lists what is
  and is not reachable from the widgets. HOLD, the price minimum, and the
  BUY-versus-cash half of the budget check are not reachable from the widgets.

**What it does not prove.** It exercises the decision function, not persistence.
`apply_trade()` is not run, no ledger row is written, and no agent is called. It
is not evidence that the live dashboard works, and its "demo · MODERATE" pill is
a label, not an account.

## 2. Decision-detail replay

This loads the three recorded synthetic fixtures into the local database and
prints the evidence a reviewer needs for one decision: the verdict, the guard
comparison, the rebuttals and the outcomes. It is a replay of **stored payloads**
and does not call a model. It is also not the deterministic guard replay tracked
as issue #29: it does not re-evaluate the guard against a recorded proposal.

**Commands:**

```bash
venv/bin/python manage.py migrate
venv/bin/python manage.py load_decision_fixtures
venv/bin/python manage.py shell -c "
import json
from core.decision_models import DecisionRun
from core.decision_serializers import build_run_detail
for fixture_id in (
    'risk-intervention-aapl-2026-02-03',
    'disagreement-tsla-2026-02-04',
    'uncertainty-msft-2026-02-05',
):
    run = DecisionRun.objects.get(fixture_id=fixture_id)
    d = build_run_detail(run)
    guard = d['guard'] or {}
    print(json.dumps({
        'fixture_id': fixture_id,
        'mode': run.mode,
        'source': run.source,
        'has_rebuttals': d['has_rebuttals'],
        'verdict': {k: d['verdict'][k] for k in ('action', 'strongest_objection')},
        'guard': {k: guard.get(k) for k in
                  ('status', 'requested_quantity', 'allowed_quantity', 'binding_rule')},
        'outcomes': [{k: o.get(k) for k in
                      ('horizon_days', 'maturity', 'forward_return_pct',
                       'benchmark_return_pct', 'unavailable_reason')}
                     for o in d['outcomes']],
    }, indent=2))
"
```

**What it needs.** PostgreSQL (the `db` service), the migrated schema, and the
fixture manifest in `docs/spec/fixtures/` (committed). No Redis, no API key, no
network. The loader is idempotent: a second run prints `SKIP` for each fixture
and writes nothing.

**What it produces.** Three JSON blocks. The values to check:

| Fixture | `mode` / `source` | Key values |
| --- | --- | --- |
| `risk-intervention-aapl-2026-02-03` | `synthetic` / `fixture` | `has_rebuttals: false`; `verdict.action: "BUY"`; guard `clamped`, requested `40.00000000`, allowed `2.00000000`, binding `max_trade_allocation_pct`; 7-day outcome `evaluated`, `-2.0000`, SPY `-0.4000` |
| `disagreement-tsla-2026-02-04` | `synthetic` / `fixture` | `has_rebuttals: true`; `verdict.action: "HOLD"`; no guard record; strongest objection "The storage segment is too small to support a 58x forward multiple."; 7-day outcome `pending` |
| `uncertainty-msft-2026-02-05` | `synthetic` / `fixture` | `has_rebuttals: false`; `verdict.action: "HOLD"`; 1-day outcome `unavailable` with a reason rather than a zero |

**What to look for.** `mode` and `source` on every block. The absence of a guard
record for a HOLD is correct, not missing evidence. The `unavailable` outcome is
a measured absence, not a score of zero. The 1-day AAPL outcome is `pending`, so
do not read the 7-day result as a summary of all horizons.

**The same payload over HTTP.** `GET /api/decision-runs/<id>/detail/` returns the
same detail object, authenticated and scoped to the caller's portfolio. The
endpoints are listed in
[`../wiki/API-Reference.md`](../wiki/API-Reference.md). The `demo` account the
loader creates has an unusable password by design — it is a fixture account, not
a login. To use the browser or the API, create the login first with
`venv/bin/python manage.py seed_demo`, then load the fixtures under that user.

**What it does not prove.** The fixtures are `mode: "synthetic"`. They exercise
the consumer contract and the evidence shape; they are not a recording of a live
debate, and the outcome figures are illustrative. See [`CASES.md`](CASES.md) for
the per-case evidence.

## 3. Paper allocation (Phase 4)

**Command:**

```bash
venv/bin/python manage.py run_allocation --reset --apply
```

**What it needs.** PostgreSQL and the migration that adds the Phase 4 tables.
No model key and no network: `services/portfolio_allocation.StaticAllocationClient`
returns the fixture's authored response, and the provenance is recorded as
`provider: stub`, `model: stub-model`.

**What it produces.** A JSON document with four phases: `brief` (holdings, cash,
equity, weights, exposure, limits, covariance/correlation, candidate cases),
`targets` (requested versus constrained weights and every deviation), `plan`
(legs, funding, estimates, constraints) and `application` (plan status,
transaction ids, holdings and cash after). It also writes the plan and, with
`--apply`, three ledger rows against the `demo-allocation` account.

**Expected values**, captured in
[`fixtures/phase4-allocation.v1.output.json`](fixtures/phase4-allocation.v1.output.json):

- equity `20000.00`, cash `10000.00`, one AAPL holding of `100` shares at
  `100.00`;
- requested weights AAPL `0.200000`, MSFT `0.250000`, JPM `0.150000`, XYZ
  `0.050000`, CASH `0.350000`;
- target weights AAPL `0.200000`, MSFT `0`, JPM `0.150000`, XYZ `0.050000`, CASH
  `0.600000`, sum `1.000000`;
- the MSFT decline is a `max_sector_weight_new_risk` deviation: technology is
  already at 50% against a 40% ceiling (effective `0.3997000` after the cost
  reserve), so new risk in that sector goes to cash;
- JPM and XYZ are reduced by lot rounding and recorded as `lot_rounding`;
- applied legs: SELL AAPL `60`, BUY JPM `18`, BUY XYZ `11`; cash after
  `12130.00`; three ledger rows.

**What to look for.** The requested MSFT weight is **not** silently dropped: it
is 0 in `target_weights` and 0.25 in `requested_target_weights`, with a
deviation that names the rule and the effective limit. Every difference between
requested and applied is recorded. The plan's `model_metadata.provider` is
`stub`, and the fixture says `synthetic: true`.

**Failure demonstration:**

```bash
venv/bin/python manage.py run_allocation --reset --apply --fail-leg AAPL
```

This removes AAPL's current mark at apply time. The command prints an
`application_failed` block with `error_type: "PlanLegFailed"` and the reason
`price_unavailable: No current quote was supplied for AAPL; refusing to size a
fill from a stale mark.` The plan status is `failed`, the AAPL leg is `failed`,
the JPM and XYZ legs are `skipped` with no transaction id, and the account has
**zero** ledger rows. That is the atomicity claim in executable form.

**What it does not prove.** The fixture is not market data and the plan is not a
return forecast. The model is a stub. The transaction costs are planning
estimates, not recorded fees. See [`ALLOCATION.md`](ALLOCATION.md) §7 and
[`CASES.md`](CASES.md) Case 5.

## 3a. Advisory plan review and recorded provider run (FIX-08)

The paper command above is still the **stub** demonstration. FIX-08 adds the
authenticated workflow the review asked for, and one real recorded provider run.

**Review surface.** Start the app and open `#/plans`, or use the API:

```text
POST /api/decision-runs/          202 + run_id + status_url (idempotent; no trade)
GET  /api/decision-runs/<run>/status/   queued/running/succeeded/failed/cancelled/timed_out
POST /api/decision-runs/<run>/cancel/   cancel an open submission
GET  /api/portfolio-plans/
GET  /api/portfolio-plans/<plan>/
POST /api/portfolio-plans/<plan>/approve/    exact plan_version + expiry; no trade
POST /api/portfolio-plans/<plan>/reject/     reason required; audit event
POST /api/portfolio-plans/<plan>/cancel/     audit event
POST /api/portfolio-plans/<plan>/apply/      explicit execution through the guard
```

The review screen shows current holdings/weights, requested vs constrained
targets, cash and sector effects, funding, cost estimates, rejected
alternatives, limitations, provenance (live provider vs **stub — no model
call**), and the exact version/expiry an approval covers.

**The analysis runs in a worker.** The `POST` returns from the durable
`queued` row; it does not call the model. Run the Celery worker (the compose
`worker` service or `celery -A config worker`) and poll the status URL. The
existing beat schedule runs `recover_allocation_submissions_task` every minute:
it re-publishes a queued row that was never published or whose publish failed,
times out a past-deadline row, fails an unreconciled paid call, and re-queues a
worker whose lease expired - all under a row lock, so an active lease and a
terminal row are left alone. No second POST and no manual command is needed.
`python manage.py repair_allocation_submissions` remains the inspection path;
it is dry run by default and `--execute` applies the same actions. A cancelled
or timed-out submission has no plan, and only an approved plan can reach
`apply`. The status URL publishes `dispatch`, `recovered`, `recovery` and the
input snapshot/source next to the six states.

**The recorded run, without making another call.** Read
[`fixtures/fix08-live-allocation.v1.json`](fixtures/fix08-live-allocation.v1.json).
It is a real Anthropic `claude-haiku-5-5` response (`mode: "live"`,
`source: "anthropic"`, 5005 input / 3020 output tokens, estimated `$0.002010`,
billed `null`, plan `proposed`, `traded: false`). Its **input brief** is
operator-supplied demonstration data; the artifact states that separately.

**Do not run the recorder casually.** `python manage.py record_live_allocation`
makes one real, billed provider call, has no stub mode, and refuses to overwrite
the committed artifact without `--overwrite`. Reproduce only its *shape*: the
prompt and template version are recorded; the model answer is not reproducible.

The recorder refuses a dirty tree, a missing acceptance record, or a record
whose verdict did not pass, and writes the record's commit and digest into the
artefact's `recording` block. The committed FIX-08 artefact predates that
mechanism, so its block was attached when the mechanism was introduced and says
so via its `status` and `provenance_kind` fields rather than pretending the
recorder emitted it. `python manage.py check_recordings` verifies the pairing;
see [`ACCEPTANCE.md`](ACCEPTANCE.md).

## 4. Report build (Phase 3)

**Commands:**

```bash
venv/bin/python manage.py load_decision_fixtures
venv/bin/python manage.py build_experiment
```

**What it needs.** PostgreSQL, the three decision fixtures, and the experiment
manifest at
`docs/spec/fixtures/experiments/phase3-engineering.v1.json` (committed). No
Redis, no model key, no market-data call: `build_experiment` imports no agent
module.

**What it produces.** A stored experiment report and a compact console summary:

```text
Experiment: phase3-engineering.v1
BUILT  phase3-engineering.v1 -> experiment <uuid> (report v1)
  scheduled=4 completed=3 failed=0 not_executed=1
  V0 Deterministic baseline: no_completed_runs (scheduled=1, completed=0, failed=0)
  V1 One analyst: measured (scheduled=1, completed=1, failed=0)
  V2 Current pipeline: measured (scheduled=1, completed=1, failed=0)
  V3 Explicit rebuttal: measured (scheduled=1, completed=1, failed=0)
  V4 Portfolio allocation: unimplemented (scheduled=0, completed=0, failed=0)
  signal observations=4 evaluated=1 unresolved=3
  portfolio performance: twr=1.3737% net_of_llm=1.3712% max_drawdown=-0.5250% approximate=True
  report: {"experiment_id": "phase3-engineering.v1", "report_version": <n>,
           "engineering_validation_only": true, "no_profitability_claim": true}
Done. No LLM or market-data request was made; the report was built from stored rows and the manifest.
```

The report version increments on every rebuild; on a clean database the first
build is version 1. The report itself is stored on the `Experiment` row and is
served at `GET /api/experiments/<id>/report/`. A committed snapshot of one build
is at
[`fixtures/experiments/phase3-engineering.v1.report.json`](fixtures/experiments/phase3-engineering.v1.report.json).

**Print the claim boundary from the stored report:**

```bash
venv/bin/python manage.py shell -c "
import json
from core.measurement_models import Experiment
r = Experiment.objects.get(experiment_key='phase3-engineering.v1').report
print(json.dumps({
  'counts': r['sample_integrity']['counts'],
  'source_mode': r['sample_integrity']['source_mode'],
  'engineering_validation_only': r['engineering_validation_only'],
  'no_profitability_claim': r['no_profitability_claim'],
  'strict_historical_claims':
      r['sample_integrity']['eligibility']['strict_historical_claims'],
  'twr_pct': r['portfolio_performance']['time_weighted_return_pct'],
  'twr_approximate': r['portfolio_performance']['approximate'],
  'sharpe': r['portfolio_performance']['risk_adjusted']['sharpe']['value'],
  'counterfactual_rows': len(r['counterfactuals']['rows']),
  'limitations': [row['code'] for row in r['limitations']],
}, indent=2))
"
```

**Expected values.** `scheduled: 4`, `completed: 3`, `not_executed: 1`,
`source_mode: "synthetic"`, `engineering_validation_only: true`,
`no_profitability_claim: true`, `strict_historical_claims: false`, TWR
`"1.3737"` with `twr_approximate: true`, `sharpe: null`,
`counterfactual_rows: 0`, and the limitation codes `per_decision_not_summable`,
`approximate_twr`, `fees_unrecorded`, `not_strict_historical`,
`synthetic_content`, `sample_below_minimum`, `variant_V4_unimplemented`.

**What to look for.** The report tells a reviewer what it cannot support before
it shows a number: no profitability claim, no strict historical claim, one
usable observation against a pre-registered minimum of two, V4 null rather than
zero, Sharpe absent rather than approximated, and zero counterfactual rows. The
accounting return is a synthetic fixture; it is not the demo account's history.

**Rebuild semantics.** Running `build_experiment` again rebuilds from the stored
rows and increments `report_version`; it does not create a second experiment for
the same `(portfolio, experiment_id)`. A manifest edit is refused unless
`--force` is passed, because a changed checksum must not be silently mixed with
old rows.

## 5. Offline decision viewer (no database)

This is REP-02's no-database viewer. It is a static, read-only page that plays a
versioned, checksummed fixture bundle. Unlike section 2 it needs no PostgreSQL,
no migrated schema, no Django process and no login.

**Commands:**

```bash
cd /root/projects/AlphaAgent
npm --prefix frontend run build:viewer
cd docs/viewer
python3 -m http.server 8777
# open http://127.0.0.1:8777/
```

Opening `docs/viewer/index.html` directly from disk also works: the default
bundle is embedded in the page, and a served copy loads the relative
`decision-runs.v1.bundle.json`. A file picker accepts another bundle — including
a redacted `GET /api/decision-runs/<id>/export/` capture — without uploading it.

**What it needs.** Node and the frontend dependencies for the one-time build. No
database, no `.env`, no Redis, no API key, no provider key and no network at run
time. The emitted page is a single self-contained `index.html` plus the bundle
JSON.

**What it produces.** Three stored synthetic runs from
`docs/spec/fixtures/decision-runs.v1.json` — the risk-intervention AAPL case, the
disagreement TSLA case (with two rebuttals) and the uncertainty MSFT case. Each
run has a visible source label, a replay timeline, a compressed/recorded timing
choice, the as-of claim/evidence/verdict/guard state, and the same evidence
drawer as the authenticated application.

**What to look for.**

- The source label is **Synthetic** on every committed fixture. The committed
  API export sample is authored too: its `run.origin` is
  `authored_fixture`, so it renders **Synthetic**. Only an export whose
  `run.origin` is `provider_run` with `provider_backed: true` renders **Real
  recorded**; that label is not inferred from the file name or from a recorded
  mode alone. The origin's limitations are displayed with the label.
- A cursor before adjudication shows no verdict, no strongest objection and no
  guard; the final summary is pinned separately and labelled as outside the replay
  scene.
- Timing is explicit: **Compressed timing** (fixed 800 ms per event at 1×) or
  **Recorded-time playback** (stored event timestamps).
- Selecting a targeted response highlights its actual target claim and the
  evidence linked to that claim.
- The browser rejects an unsupported schema version and a corrupted envelope or
  per-run SHA-256 checksum with a concrete message. The file is not partially
  rendered.
- There is no approve, execute, run-agent, autonomy or live-refresh control. The
  CSP and fetch guard allow only the relative fixture bundle; external evidence
  URLs are shown as text, never as clickable links.
- `frontend/viewer/scripts/review-export.mjs` scans every free-text value and
  URL, not just sensitive key names, and is part of `build:viewer`.

**What it does not prove.** The committed bundle is synthetic. It does not
re-evaluate the guard, re-run attribution, prove a real recording is authentic,
or establish profitability. A `real recorded` label is a bundle claim; the
export endpoint and the reviewer's handling of the file establish authenticity.

Full details, bundle format and export-review rules:
[`frontend/viewer/README.md`](../../frontend/viewer/README.md).

## Common failures

| Symptom | Cause | Fix |
| --- | --- | --- |
| `ImproperlyConfigured: POSTGRES_PASSWORD ...` | No `.env`, or the variable is empty | `cp .env.example .env` and set the two mandatory values |
| `connection refused` on port 5432 | The data tier is not running | `docker compose up -d db redis` |
| Streamlit cannot import `services` | Started outside the repository root | Run `streamlit run demo/app.py` from the repository root |
| `load_decision_fixtures` prints `SKIP` | The fixture ids are already loaded (the loader keys on `fixture_id`, not on the user) | Use the existing runs, or `--force` only when the manifest checksum changed |
| `build_experiment` reports `not_executed` for V1–V3 | The fixtures were not loaded first | Run `load_decision_fixtures` before `build_experiment` |
| The viewer says "Bundle rejected" with a checksum error | The file was edited after its checksum was written, or a text editor changed bytes | Use the unmodified export, or rebuild the fixture bundle with `npm --prefix frontend run viewer:fixtures` |
| The viewer says "Unsupported schema version" | The bundle was produced by a newer format | Use a bundle with version 1.0; the message names the version this viewer supports |
| The `demo` account cannot log in | The fixture loader deliberately creates an unusable password | `manage.py seed_demo` first, then load fixtures under that user |

## What these demonstrations do not establish

They do not establish profitability, a live-model result, a protocol comparison
or a guard that prevented a loss. The evidence classes and the prohibited claims
are in [`METHODOLOGY.md`](METHODOLOGY.md) §6; the reviewed cases, including
their synthetic labels, are in [`CASES.md`](CASES.md).
